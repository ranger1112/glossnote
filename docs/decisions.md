## D1 独立新仓库

**背景**：曾讨论直接扩展已有的 FlashNote（速记小窗），复用其 Tauri、托盘、更新器与 WebDAV 同步。

**决定**：新建 `glossnote` 仓库，独立产品、独立发布。

**理由**：速记浮窗与“书库 + 阅读器”是两种产品形态，窗口模型、前端状态量和发布风险都不同；混在一个应用里会让速记用户被动接收一个阅读器。独立仓库可以先把核心体验做好，同步/更新器等基础设施需要时再移植。

**代价**：暂时不能复用 FlashNote 的同步引擎；发布流程要重新搭一遍。接受。

## D2 PDF 优先

**背景**：目标支持 PDF / HTML / EPUB / TXT。

**决定**：第一版只做 PDF，其他格式推迟到 1.0。

**理由**：PDF 固定版式，坐标锚定最稳，能最快验证“标注保真”这个核心风险；HTML 需要冻存快照，EPUB 可重排，都会显著拉长第一个版本。

**代价**：网页长文用户要等更久。`AnchorStrategy` 接口在 1.0 前抽象好，减少返工。

## D3 导入即入库

**背景**：可以让应用引用用户原有目录，也可以复制进应用书库。

**决定**：导入时复制到 `<Library>/books/`，书库根目录可配置（可指向云盘同步目录）。按内容哈希去重。

**理由**：客户端内完成“导入 → 阅读 → 标注”，用户不需要管理文件路径；云盘同步以整个书库为单位；文件名可读。哈希去重避免同一文件导入两次。

**代价**：占用双份磁盘空间；外部修改原文件不会同步到书库。接受，书库是唯一工作副本。

## D4 SQLite 索引 + 哈希 sidecar

**背景**：标注存在哪里，决定了多端同步与数据可迁移性。

**决定**：本地 SQLite 作为工作库；每份文档的标注同时写到 `<Library>/.glossnote/annotations/<sha256>.json`。SQLite 可删除重建。

**理由**：SQLite 查询快、支持 FTS5；sidecar 是明文、可读、可脚本处理，随云盘走。按哈希命名避免文件重命名/移动导致失联；隐藏目录保持书库顶层干净。

**代价**：写标注要同时维护两份数据，需要防抖与崩溃一致性；sidecar 明文，不提供静态加密。接受，可靠性优先。

**放弃的方案**：标注 JSON 直接放在 PDF 旁边（文件多、改名易失联）；只存 SQLite（不可移植）；只存 JSON（搜索与列表性能差）。

## D5 同步用 LWW + 墓碑，不上 CRDT

**背景**：多端同步需要冲突处理。

**决定**：按 `annotation.id` 对齐，`updated_at` 新者胜；删除写墓碑；保留冲突副本以便追溯。暂不引入 Yjs / Automerge。

**理由**：标注是准不可变的小记录，天然适合逐条合并；CRDT 会显著增加存储、调试和迁移成本。只有“两人同时编辑同一段笔记正文”成为真实需求时才重新评估。

**代价**：同一毫秒内的并发修改可能丢一个版本；通过冲突副本兜底。

## D6 Tauri 2 + React + pdf.js

**背景**：需要桌面壳、UI 框架与 PDF 渲染/文本层。

**决定**：Tauri 2 + React + TypeScript + pdf.js。

**理由**：Tauri 体积与内存友好，Rust 适合做文件、哈希与 SQLite；React 适合阅读器这种多状态界面；pdf.js 提供 canvas 渲染和可选择的文本层，是锚定的基础。

**代价**：WebView 的 CSP、worker 与 WASM 需要额外验证；与纯原生相比，超大 PDF 的性能上限略低。

## D7 四级锚定回退 + 归一化坐标

**背景**：标注必须在缩放、重开、文档轻微变化后仍然可用。

**决定**：保存页文本哈希、字符偏移、quote、前后文与归一化矩形；解析时依次走 exact → 文本查找消歧 → 相似度匹配 → 比例估算。

**理由**：单一策略都会在某种情况下失效；W3C Web Annotation 的回退链是经过验证的做法。归一化坐标与缩放解耦。

**代价**：实现与测试成本高于“存像素矩形”；最后一档只能是低置信度提示。

## D8 手写只预留

**背景**：平板手写是自然需求，但会改变输入、渲染与数据结构。

**决定**：0.x 不实现手写，但坐标保持归一化、`kind` 枚举预留 `ink`、输入统一走 Pointer Events、标注层独立于文本层。

**理由**：先验证文本标注的核心价值；预留成本很低，后补成本很高。

## D9 AI 结论必须能锚回原文

**背景**：AI 总结与问答很容易变成无法验证的 ChatPDF。

**决定**：阅读中的解释看到当前段落上下文；阅读后的 RAG 只基于用户文档与标注，回答必须带引用并能跳回原文。

**理由**：可验证性是“沉淀”和“学习”的信任基础，也是与通用 ChatPDF 的差异点。

**代价**：切块、引用与跳转的工程成本更高；模型输出需要约束格式。

## D10 命名 GlossNote / 旁注

**背景**：需要与 FlashNote 形成品牌家族，同时能覆盖标注、知识库与 AI。

**决定**：英文 GlossNote，中文暂定「旁注」，仓库 `glossnote`，标识符 `com.phoebe.glossnote`。

**理由**：gloss 指页边解释，直接对应产品动作；两词组合易读易拼；与 FlashNote 的 `-Note` 后缀一致。

**代价**：描述性组合的商标保护较弱；“gloss”一词多义，中文名承担主要识别。商业化前重新评估商标与域名。

## D11 单窗口双视图

**背景**：曾考虑速记浮窗 + 资料库窗口的双窗口结构（沿用 FlashNote 的形态）。

**决定**：GlossNote 第一版只有一个主窗口，内部切换书库与阅读器；不做全局速记浮窗。

**理由**：书库与阅读器共享大量状态，单窗口切换更简单；速记是另一个产品的核心，不应拖慢第一版。

**代价**：阅读时想快速记一笔，需要先切回应用。若该需求高频，再评估浮窗。

## D12 原型用 localStorage（临时）

**背景**：0.1 需要最快验证锚定，不应被数据库与文件系统拖慢。

**决定**：浏览器原型用 `localStorage` 保存文档记录与标注。

**理由**：零依赖、刷新即验证；`storage.ts` 作为唯一读写边界，替换时 UI 不动。

**代价**：容量有限、无并发保护、不能跨设备。0.3 必须替换为 SQLite + sidecar，此项标记为临时。
